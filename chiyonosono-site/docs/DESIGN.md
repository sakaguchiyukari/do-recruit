## ① サイトコンセプト

### コンセプトステートメント（第1案・推奨）

> # 米を、識る。
> ### 明治二十九年、米問屋から始まった酒蔵です。

### なぜこの案か

酒蔵サイトは全国に数百あり、その多くが「伝統」「こだわり」「手造り」という**交換可能な言葉**で自らを語っています。
それらは事実ではあっても、差別化にはなりません。

千代の園酒造には、他の蔵が言えない事実が一つあります。

**「米問屋が始めた酒蔵であり、酒米の品種そのものを作った」**（九州神力）

酒を語る蔵は多い。しかし**米から語れる蔵**は稀です。
「識る（しる）」という字を選んだのは、「知る」より深く、**目利きする・見分ける**という米問屋の職能を含む語だからです。
このコンセプトなら、以下がすべて一本の線で繋がります。

- 沿革（米問屋 → 酒蔵）
- 九州神力の作出
- 商品ページで精米歩合や品種を丁寧に語る必然性
- ブログで「今年の米の出来」を書き続ける必然性

### コンセプト第2案・第3案（ご選択ください）

| 案 | ステートメント | 訴求の軸 | 向いている場合 |
|---|---|---|---|
| 第2案 | **一粒に、百二十年。** | 歴史・継承 | 老舗としての格を最優先したい |
| 第3案 | **熊本の、赤い酒。** | 赤酒・地域文化 | 赤酒を事業の主役に据えたい |

> 本書の以降の記述は**第1案を前提**に書いています。

### サイトが果たす役割（優先順位）

| 優先 | 役割 | 主ターゲット | サイト上の担保 |
|---|---|---|---|
| 1 | **ブランド価値の向上** | 日本酒ファン・飲食店・バイヤー | 米を軸にした物語／写真の質／余白 |
| 2 | **商品を正しく伝える** | 購入検討者・酒販店 | スペックを省略しない商品詳細／ウェブショップへの明快な導線 |
| 3 | **来訪の促進** | 観光客（山鹿温泉・八千代座の来訪者） | 資料館・売店情報／地図／営業時間／**工場見学不可の明記** |
| 4 | **蔵の「今」を伝え続ける** | 全員・検索エンジン | ブログ（microCMS運用）／仕込みの季節感 |
| 5 | **業務用・卸の問い合わせ受け** | 飲食店・小売・メディア | 用途を選べる問い合わせフォーム |

### 3つの設計原則

1. **写真が語り、文字は補う。**
   麹・米・蔵の質感が主役。説明文は減らし「刺さる一行」を置く。
2. **カードグリッドで並べない。**
   3カラムのアイコン付きカードはテンプレート感の正体。全幅の**帯（Band）**と**罫線のリスト（Rule List）**で構成する。
   （※商品一覧のみ例外的にグリッドを使うが、影を落とさず罫線で仕切る）
3. **1画面に1メッセージ。**
   スクロールごとに伝わることを1つに絞る。

### やらないこと（禁止事項の明文化）

- ❌ 3カラムのアイコン付きカードグリッド（商品一覧を除く）
- ❌ 影の強いカード（`box-shadow` は `0 1px 2px` 相当まで）
- ❌ 背景の斜め図形・装飾グラデーション
- ❌ 派手なガラスモーフィズム（ヘッダー背景に極薄く使うのみ）
- ❌ 角丸999pxの塗りボタンを主役にする（Bootstrap感の正体）
- ❌ 中央揃えの短文の連続（左揃え基調で紙面に軸を通す）
- ❌ 筆文字フォントの多用（1箇所のみ許容。多用は「古いサイト感」に直結）
- ❌ 桜・扇・和柄背景のクリップアート
- ❌ アニメーションの多重掛け（1要素1アニメーション）

## ② デザインコンセプト

### キービジュアル思想：「和紙の余白と、墨の一本線」

サイト全体に **`--rule` という1pxのヘアライン** を通し続けます。
セクション区切り、リスト区切り、見出しの下線——すべて同じ太さ・同じ色。
装飾を線1本に集約し、**写真と余白だけが残る紙面**をつくります。

背景は純白ではなく、**生成り（きなり）**の和紙色 `#faf8f4` を基調にします。
純白 `#ffffff` は「ブラウザのデフォルト」に見え、和の質感が出ません。

### 版面設計（グリッド）

| 項目 | 値 |
|---|---|
| 最大コンテンツ幅 | `1200px`（`--container-max`） |
| 読み物（ブログ本文）幅 | `720px`（`--container-read`）— 和文1行 38〜42字を守る |
| 全幅セクション | 画面幅100%（写真帯・引用帯） |
| 左右パディング | `clamp(20px, 5vw, 64px)` |
| カラム | PC 12カラム／TB 8カラム／SP 4カラム（`grid` で表現、フレームワークは使わない） |

### 「余白設計」の定義（数値で握る）

余白は感覚ではなく**トークンで固定**します。

| トークン | 値 | 用途 |
|---|---|---|
| `--space-section` | `clamp(72px, 12vw, 160px)` | セクション間の縦余白 |
| `--space-block` | `clamp(40px, 6vw, 80px)` | セクション内ブロック間 |
| `--space-item` | `clamp(20px, 3vw, 32px)` | 要素間 |
| `--space-inline` | `clamp(12px, 2vw, 20px)` | 文中・ボタン内 |

> 原則：**セクション間余白 ≧ 見出しの高さ × 2**。これを下回ると「詰まった古いサイト」に見えます。

### 写真の扱い

- **切り抜き・角丸を多用しない。** 四角のまま大きく置く（角丸は `4px` まで）
- 人物は「作業中の手元」を優先。ポーズ写真は使わない
- 商品写真は**背景を生成り一色**に統一（撮影ガイドを⑥章に記載）
- 写真上に文字を乗せる場合は必ず**グラデーションマスク**を敷き、コントラスト比 4.5:1 以上を確保

### トーン&マナー参照（言語化）

| 軸 | 目指す位置 |
|---|---|
| 古典 ←→ 現代 | **やや現代寄り**（素材は伝統、レイアウトは現代の余白設計） |
| 静 ←→ 動 | **静**（アニメーションは「気づかれない程度」に留める） |
| 情報密度 | **低**（1画面1メッセージ） |
| 色数 | **少**（生成り＋墨＋赤酒色の3色。金は差し色として面積1%以下） |

### URL設計ルール

1. **末尾スラッシュのディレクトリ形式**（`/about/` = `about/index.html`）。`.html` を露出させない
2. 静的ファイル配置は URL と1対1（`/products/sake/` → `products/sake/index.html`）
3. 記事の slug は**英数字ハイフン**。日本語URLは使わない
4. **既存ブログのURLは可能な限り維持する。** 変わる場合は必ず301リダイレクト（⑪章）

### グローバルナビゲーション

```
蔵について ／ 商品 ／ 赤酒とは ／ 資料館・売店 ／ ブログ ／ お問い合わせ   [ オンラインショップ ▸ ]
```

- 7項目まで。これを超えたら情報設計の失敗と判断する
- 「オンラインショップ」のみ**枠線ボタン**で区別（外部遷移であることを明示）
- SP は右上ハンバーガー → 全画面ドロワー
- **SP では画面下に固定CTAバー**（「オンラインショップ」「お問い合わせ」の2分割）を配置し、CTAを埋もれさせない

### パンくずリスト

全下層ページに設置し、`JSON-LD (BreadcrumbList)` を併記。TOPには置かない。

### 酒類サイトとしての必須対応【要確認：法務確認を推奨】

酒類製造業者のサイトには、業界の自主基準に基づく以下の対応が一般的です。

1. **サイト初回訪問時の年齢確認**（「あなたは20歳以上ですか」モーダル。`localStorage` で1回だけ表示）
2. **全ページフッターに「20歳未満の者の飲酒は法律で禁止されています」「飲酒運転は法律で禁止されています」**
3. 妊娠中・授乳期の飲酒に関する注意表記

> 年齢確認モーダルは**離脱率とのトレードオフ**があります。実施要否は蔵元様のご判断をお願いします。【推測】

> **「CSSは1ファイル」条件への対応**

> `style.css` は `@import` で各層を結合します。`@import` は追加リクエストを生むため、

### CSS設計方針（BEM ＋ FLOCSS レイヤリング）

**命名規則（BEM）**

```
.block__element--modifier
```

| 層 | プレフィックス | 例 |
|---|---|---|
| Layout | `l-` | `.l-header`, `.l-section` |
| Component | `c-` | `.c-button`, `.c-button--outline`, `.c-rule-list__item` |
| Project | `p-` | `.p-hero`, `.p-hero__title`, `.p-products__item` |
| Utility | `u-` | `.u-visually-hidden` |
| 状態 | `is-` / `js-` | `.is-open`（状態）／`.js-drawer`（JS参照専用・スタイル禁止） |

**厳守ルール**

1. 色・余白・フォントサイズの**生の値は `_variables.css` にのみ**書く。他層は `var()` 経由
2. **要素セレクタ・IDセレクタでスタイルを当てない**（`_reset.css` / `_base.css` を除く）
3. ネストは**2階層まで**。詳細度を上げない
4. `!important` は `utility` 層のみ許可
5. **JSが触るクラスは `js-` を付け、CSSからは参照しない**（デザイン変更でJSが壊れるのを防ぐ）
6. メディアクエリは**そのコンポーネントのファイル内**に書く（分離しない）

**ブレイクポイント**

| 名称 | 値 | 対象 |
|---|---|---|
| SP | 〜 `599px` | スマートフォン |
| TB | `600px` 〜 `959px` | タブレット |
| PC | `960px` 〜 | デスクトップ |
| Wide | `1400px` 〜 | 大画面（コンテナ幅で頭打ち） |

モバイルファースト（`min-width` で加算）で記述します。

### JavaScript 設計方針

**方針：必要最低限。JSが無効でもコンテンツは全て読める。**

| モジュール | 責務 | JS無効時 |
|---|---|---|
| `drawer.js` | SPドロワーの開閉、フォーカストラップ、`aria-expanded` | ナビはフッターに同内容あり |
| `header.js` | スクロール量でヘッダーを透過→不透明に切替 | 常時不透明 |
| `scroll-reveal.js` | **IntersectionObserver** によるフェードイン | 全要素が表示済み（CSSの初期値を可視にする） |
| `sp-cta.js` | ヒーロー通過後に下部CTAを表示（Observerを流用） | CTAは常時表示 |
| `age-gate.js` | 年齢確認モーダル。`localStorage` に1回記録 | モーダルは出ない（コンテンツは閲覧可） |
| `form-validate.js` | HTML標準バリデーションのメッセージ整形のみ | ブラウザ標準の検証が動作 |
| `utils.js` | `$$`, `prefersReducedMotion()` 等の共通関数 | — |

- **jQuery不使用。** 素のDOM APIのみ
- `var` は使わない。`const` / `let` のみ
- 全モジュールは ES Modules。`<script type="module" src="/assets/js/main.js" defer></script>`
- **DOM取得は必ず null チェック**（同じ `main.js` を全ページで読むため、要素が無いページで落とさない）

## ⑥ 画像の使用指示

### 撮影・選定の全体方針

1. **「工程」を撮る。** 完成品より、洗米・蒸米・麹・櫂入れといった**動きのある手元**を優先
2. **人の顔より手を。** 蔵人の手・道具・米の質感
3. **自然光基調。** ストロボの硬い影を避ける。蔵内は暗いのでISOを上げてでも自然光で
4. **横位置優先。** ヒーロー・全幅バンドで使うため 16:9 と 3:2 を確保

6. **NG：** 過度なHDR、彩度を上げた「観光パンフレット的」な色、和柄の合成、フリー素材の外国人モデル

## ⑧ カラーパレット

### 設計思想

**「和紙・墨・赤酒」の3色。** 色数を絞ることが、そのまま品格になります。

- **地は生成り**：純白 `#ffffff` を使わない。ブラウザのデフォルトに見えるため
- **文字は墨**：純黒 `#000000` を使わない。和文が硬く重くなるため
- **差し色は赤酒**：熊本の御国酒である赤酒の赤褐色。この蔵にしか使えない色
- **金は面積1%以下**：受賞表示・区切りの点など、極小面積のみ。多用すると一気に安くなる

ブラウザによる強制的な色反転を防ぎます。【推測：ご要望があれば再検討します】

## ⑨ フォント設計

### 使用フォント

| 用途 | フォント | 理由 |
|---|---|---|
| 和文（本文・見出し） | **Noto Serif JP**（明朝） | 酒蔵の品格は明朝でしか出ない。ゴシック主体は「今どきの企業サイト」になり蔵らしさが消える |
| 和文（UI・注記・フォーム） | **Noto Sans JP**（ゴシック） | 小さい文字・フォーム・タグは明朝だと可読性が落ちるため使い分ける |

| ロゴ・キーコピー | **画像（SVG）** | 既存ロゴの字形を再現するため、Webフォントに頼らない |

```css
--font-serif: "Noto Serif JP", "Hiragino Mincho ProN", "Yu Mincho", serif;
--font-sans:  "Noto Sans JP", "Hiragino Sans", "Yu Gothic", sans-serif;
```

**読み込み方針（パフォーマンス）**

- Google Fonts から `display=swap` で読み込む
- **ウェイトは Serif 400/600、Sans 400/500 の計4種のみ。** 増やすほど遅くなる
- `<link rel="preconnect">` を `fonts.googleapis.com` / `fonts.gstatic.com` に付与
- 【要判断】表示速度を最優先する場合は、**必要字形だけをサブセット化して自ホスティング**する選択肢もあります（日本語フォントは1ウェイトあたり数MBのため効果が大きい）

| トークン | 値 | 用途 |
|---|---|---|
| `--fs-hero` | `clamp(2.25rem, 6vw, 4.5rem)` | ヒーロー大見出し |
| `--fs-h2` | `clamp(1.75rem, 4vw, 3rem)` | セクション見出し |
| `--fs-h3` | `clamp(1.25rem, 2.4vw, 1.75rem)` | 小見出し |
| `--fs-lead` | `clamp(1.0625rem, 1.6vw, 1.25rem)` | リード文 |
| `--fs-body` | `clamp(0.9375rem, 1.2vw, 1.0625rem)` | 本文（SP 15px 〜 PC 17px） |
| `--fs-small` | `0.8125rem` | 注記・キャプション |
| `--fs-label` | `0.75rem` | タグ・章番号（`letter-spacing: .12em` を併用） |

### 行間・字間（和文の可読性設計）

| 項目 | 値 | 理由 |
|---|---|---|
| 本文 `line-height` | `1.9` | 和文は欧文より行間を広く取らないと詰まって見える |
| 見出し `line-height` | `1.4` | 大きい文字は行間を詰めないと間延びする |
| 本文 `letter-spacing` | `0.04em` | わずかに開けると明朝の品が出る |
| 見出し `letter-spacing` | `0.08em` | — |
| ラベル `letter-spacing` | `0.12em` | 小さい文字ほど広げる |
| 1行の文字数 | **38〜42字** | `--container-read: 720px` で担保 |

**改行制御**

```css
h1, h2, h3, .p-hero__title { word-break: auto-phrase; } /* 対応ブラウザで文節改行 */
p { text-wrap: pretty; }                                 /* 行末1文字の孤立を防ぐ */
```

- 対応外ブラウザでは通常改行になるだけで、崩れは起きません
- 見出しの意図的な改行は `<br>` ではなく `<wbr>` または CSS で制御し、SPで不自然な改行が起きないようにします

### 見出しレベルの意味論（アクセシビリティ）

- 1ページに `h1` は1つ。TOPは「米を、識る。」、下層はページタイトル
- **見た目の大きさで見出しレベルを選ばない。** 大きく見せたいだけなら `h2` にクラスを当てる
- 章番号（01 / 02）は装飾なので `aria-hidden="true"` の `span` にする

## ⑩ アニメーション設計

### 基本原則

1. **1要素につき1アニメーション。** 移動と拡大とフェードを同時にかけない
2. **距離は短く。** 移動量は最大 `24px`。大きく動かすほど安っぽくなる
3. **速度は速く、イージングは減速。** `.6s` `cubic-bezier(.22,.61,.36,1)`
4. **一度動いたら二度と動かさない。** スクロールで戻っても再生しない（`unobserve`）
5. **`prefers-reduced-motion: reduce` では全て無効化。**

```css
--ease-out: cubic-bezier(0.22, 0.61, 0.36, 1);
--dur-fast: 0.24s;
--dur-base: 0.6s;
--dur-slow: 0.9s;
```

### アニメーション一覧

| 対象 | 動き | 時間 | 備考 |
|---|---|---|---|
| セクション要素 | `opacity 0→1` ＋ `translateY(24px→0)` | `.6s` | IntersectionObserver |
| リスト項目 | 上記＋**80ms のスタッガ** | `.6s` | `--i` カスタムプロパティで遅延 |
| ヒーロー見出し | 遅延 `.2s` のフェードアップ | `.9s` | 読み込み直後に1回 |
| 全幅バンドの写真 | `scale(1.06→1)` のゆっくりズーム | `1.4s` | 帯セクションのみ |
| リンクのホバー | 下線が左から伸びる | `.24s` | `scaleX` を使い `width` は使わない |
| ボタンのホバー | 背景色の変化＋矢印が `4px` 右へ | `.24s` | 浮き上がり（`translateY(-2px)`）は使わない |
| 商品カードのホバー | 画像のみ `scale(1.04)`、枠は動かさない | `.4s` | 影は付けない |
| ヘッダー | 透過→不透明 | `.24s` | スクロール `80px` で切替 |
| ドロワー | 右から `translateX` | `.32s` | 背景は同時にフェード |
| SP下部CTA | 下から `translateY(100%→0)` | `.32s` | ヒーロー通過で出現 |

### IntersectionObserver 実装方針

```js
// modules/scroll-reveal.js の設計
// - 対象: [data-reveal] を持つ要素
// - rootMargin: '0px 0px -12% 0px' … 画面下端より少し手前で発火
// - threshold: 0.15
// - 発火したら is-visible を付与し unobserve（再生は1回）
// - IntersectionObserver 非対応時は全要素に即 is-visible を付与
// - prefers-reduced-motion: reduce のときは Observer を作らず即 is-visible
```

```css
/* CSS側：JSが動かなくても内容が読める初期値にする */
[data-reveal] {
  opacity: 1;                     /* ← 既定は可視。JSが .js-reveal-ready を付けてから隠す */
}
.js-reveal-ready [data-reveal] {
  opacity: 0;
  transform: translateY(24px);
  transition: opacity var(--dur-base) var(--ease-out),
              transform var(--dur-base) var(--ease-out);
}
.js-reveal-ready [data-reveal].is-visible {
  opacity: 1;
  transform: none;
}
```

> **ここが要点**：CSSだけで最初から `opacity: 0` にすると、**JSが失敗した瞬間にサイトが真っ白**になります。
> 「JSが動くと確認できてから隠す」順序にすることで、その事故を構造的に防ぎます。

### モーション削減対応

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

加えて、ヒーロー動画は JS 側でも `matchMedia('(prefers-reduced-motion: reduce)')` を判定して再生しません。

## ⑪ ブログの引き継ぎ計画（静的HTML ＋ microCMS）★本リニューアルの最重要論点

### 現状の確認と、正直な前提

**現行ブログの基盤は未特定です。** 制作環境から `www.chiyonosono.co.jp` へアクセスできず、
蔵元様側でも「わからない」とのご回答でした。**基盤が特定できるまで、移行工数は確定できません。**

そこで本章は「**まず基盤を特定する手順**」から始めます。

### Step 1. 現行ブログの基盤を特定する（所要：15分）

以下をブラウザで順に確認してください。**1つでも該当すれば基盤が確定します。**

| # | 確認方法 | 該当すれば |
|---|---|---|
| 1 | ブラウザで記事ページを開き `Ctrl+U`（ソース表示）→ `generator` で検索 | `<meta name="generator" content="WordPress 6.x">` → **WordPress** |
| 2 | URL末尾に `/wp-json/wp/v2/posts` を付けてアクセス | JSONが返る → **WordPress（REST API 有効）** |
| 3 | `/feed/` または `/rss` にアクセス | RSSが返る → 記事の機械的な取得が可能 |
| 4 | ソース内に `wp-content` `wp-includes` の文字列があるか | あれば **WordPress** |
| 5 | ソース内に `static.parastorage.com`（Wix）／`jimdo` の文字列があるか | あれば **ASP型CMS** |
| 6 | 管理画面のログインURLが `/wp-admin/` か | **WordPress** |

**あわせて控えていただきたい情報**

- 記事の総数（管理画面の「投稿」件数）
- カテゴリ／タグの一覧
- 記事URLの形式（例：`/blog/2024/03/15/title/` か `/?p=123` か）
- 画像の総容量
- **サーバー・ドメインの契約先と管理画面へのアクセス可否**（移行時に必須）

### Step 2. 記事データの書き出し

| 現行基盤 | 書き出し方法 | 取得できるもの | 難易度 |
|---|---|---|---|
| **WordPress** | 管理画面 → ツール → **エクスポート** → 「投稿」→ WXR（XML）を保存 | 本文・タイトル・日付・カテゴリ・タグ・slug・画像URL | 低 |
| **WordPress（管理画面に入れない）** | `/wp-json/wp/v2/posts?per_page=100&page=N` を巡回して JSON を保存 | ほぼ同等（下書きは取得不可） | 低 |
| **ASP型（Wix/Jimdo等）** | 公式のエクスポート機能があればそれを使用。無い場合は **RSS ＋ 各記事HTMLの取得** | RSSは全文を含まない場合があり、**本文はHTMLから抽出**が必要 | 中〜高 |
| **外部ブログ（Ameba/note等）** | 各サービスのエクスポート機能／RSS | サービス依存 | 中 |

> ⚠️ **ASP型だった場合、移行工数は WordPress の2〜3倍になります。** その場合は
> 「過去記事は現行ブログを残置してリンクし、新規記事のみ microCMS」という**併存案**も選択肢としてご提案します。【推測】

### Step 3. microCMS のAPIスキーマ設計

**API 1：`blog`（リスト形式）**

| フィールドID | 表示名 | 種類 | 必須 | 備考 |
|---|---|---|---|---|
| `title` | タイトル | テキストフィールド | ✅ | |
| `slug` | スラッグ | テキストフィールド | ✅ | 英数字ハイフン。**旧URLと同一にする**（後述） |
| `body` | 本文 | リッチエディタ | ✅ | |
| `excerpt` | 抜粋 | テキストエリア | | 未入力時は本文先頭80字を自動使用 |
| `eyecatch` | アイキャッチ | 画像 | | 未設定時は既定OGP画像 |
| `category` | カテゴリ | コンテンツ参照（`category`） | ✅ | |
| `publishedAt` | 公開日 | （microCMS標準） | ✅ | **旧記事の日付を引き継ぐ** |
| `legacyUrl` | 旧記事URL | テキストフィールド | | 移行検証・リダイレクト生成用 |

**API 2：`category`（リスト形式）** — `name`／`slug`

**API 3：`news`（リスト形式）** — お知らせ。`title`／`slug`／`body`／`publishedAt`

**API 4：`settings`（オブジェクト形式）** — サイト共通のお知らせ帯など【任意】

### Step 4. microCMS へのインポート

`tools/migrate-to-microcms.mjs` を作成します。処理の流れ：

```
1. WXR(XML) または REST JSON を読み込む
2. 本文HTMLを整形
   - WordPress特有の記述（ショートコード、wp-block-*、align系クラス）を除去
   - 画像の src を、microCMS にアップロード後のURLへ差し替え
3. 画像を microCMS のメディアへアップロード
4. microCMS Content API (POST/PUT) で下書きとして投入
   - PUT /api/v1/blog/{slug}  ← IDを slug と一致させ、冪等に再実行できるようにする
5. 投入結果を CSV で出力（旧URL / 新URL / 成否）
```

- 認証：`X-MICROCMS-API-KEY`（**書き込み権限のあるAPIキー。リポジトリにコミットしない**。環境変数で渡す）
- **必ず下書き（draft）で投入し、目視確認後に一括公開**します。いきなり公開しません
- レート制限を考慮し、逐次実行＋リトライを入れます

### Step 5. 静的HTMLへのビルド

**「HTMLファイルで管理」というご要望と、microCMS の両立方法**

microCMS はデータの保管庫であり、そのままではHTMLになりません。方式は2つあります。

| 方式 | 仕組み | SEO | 運用 | 判定 |
|---|---|---|---|---|
| **A. ビルド時生成（推奨）** | `tools/build-blog.mjs` が microCMS から記事を取得し、`blog/<slug>/index.html` を**書き出す** | ◎ 完全な静的HTML。クローラに確実に読まれる | 記事公開のたびにビルド実行（Webhook で自動化可） | ✅ **採用** |
| B. クライアント取得 | ブラウザのJSが microCMS を叩いて描画 | △ JS実行に依存。OGPが動的にならずSNS共有に弱い | ビルド不要 | ❌ |

**A方式の構成**

```
microCMS（記事の保管・執筆）
   │  ① 記事を公開
   ▼
Webhook → デプロイ先（Netlify / Cloudflare Pages 等）
   │  ② ビルド実行： node tools/build-blog.mjs
   ▼
blog/<slug>/index.html を生成 → 公開
```

- テンプレートは `tools/templates/*.html` に置き、**プレースホルダ置換のみ**の素朴な実装にします
  （フレームワークを入れないことで、5年後も読めるコードにする）
- 生成対象：記事詳細／一覧（ページネーション）／カテゴリ別一覧／`sitemap.xml`／RSS
- ビルドに必要なもの：**Node.js 20以上**。蔵元様側での作業は不要（デプロイ環境で実行）

> **ご認識いただきたい点**：この方式では**Node環境でのビルド**が必要になり、
> 「HTMLファイルだけを FTP で上げる」という運用からは一歩外れます。
> ただし**成果物は純粋な静的HTML**であり、TOPや商品ページなど**ブログ以外は今まで通り手でHTMLを編集できます**。

### Step 6. URL維持と301リダイレクト（**SEO資産を失わないための最重要工程**）

**原則：旧記事URLは1本残らず新URLへ繋ぐ。**

| 旧URL形式 | 新URL | 対応 |
|---|---|---|
| `/blog/2024/03/15/harvest/` | `/blog/harvest/` | 301 |
| `/?p=123` | `/blog/<slug>/` | 301（`legacyUrl` フィールドから対応表を生成） |
| `/blog/category/news/` | `/blog/category/news/` | 変更なし |

- `tools/migrate-to-microcms.mjs` が出力するCSVから、**リダイレクト設定ファイルを自動生成**します
  - Apache の場合：`.htaccess`
  - Netlify の場合：`_redirects`
  - Cloudflare Pages の場合：`_redirects`
- 公開後の必須作業
  1. Google Search Console に新 `sitemap.xml` を送信
  2. 旧サイトの主要URLを「URL検査」でクロール依頼
  3. 公開後4週間、Search Console の 404 を毎週確認

> ⚠️ **リダイレクトの実装可否はサーバー環境に依存します。** 現在のサーバーが `.htaccess` を許可しているか、
> 移行先をどこにするかを Step 1 と併せてご確認ください。

### 移行先ホスティングについて【ご判断のお願い】

| 候補 | 静的HTML | リダイレクト | Webhookビルド | 費用 |
|---|---|---|---|---|
| 現行レンタルサーバー継続 | ○ | `.htaccess` 次第 | ✕（手動アップロード） | 現状維持 |
| **Cloudflare Pages** | ◎ | ◎ | ◎ | 無料枠あり |
| **Netlify** | ◎ | ◎ | ◎ | 無料枠あり |

> microCMS の料金プランは公開情報の変動があるため、**契約前に公式サイトで最新のプラン・API制限をご確認ください**。
> 無料枠のあるプランが提供されていますが、本書執筆時点の内容を断定できません。【要確認】

### この方式のリスク（正直に記載します）

1. **microCMS はサービス依存です。** 障害・仕様変更・料金改定の影響を受けます。ただし記事データは
   いつでもAPI経由で全件エクスポートできるため、**ロックインは軽微**です
2. **ビルドを忘れると記事が公開されません。** Webhook 連携を必ず設定します
3. **移行時に本文の体裁が崩れる箇所が必ず出ます。** 全記事の目視確認を工数に見込んでください
   （目安：100記事で3〜4時間）

### 項目定義

| 項目 | `name` | `type` | 必須 | 属性 |
|---|---|---|---|---|
| お問い合わせ種別 | `subject` | `select` | ✅ | 商品／業務用・卸／取材／資料館・売店／その他 |
| お名前 | `name` | `text` | ✅ | `autocomplete="name"` |
| 会社・店舗名 | `company` | `text` | | `autocomplete="organization"` |
| メールアドレス | `email` | `email` | ✅ | `autocomplete="email"` `inputmode="email"` |
| 電話番号 | `tel` | `tel` | | `autocomplete="tel"` `inputmode="tel"` `pattern="^[0-9\-]{10,13}$"` |
| お問い合わせ内容 | `message` | `textarea` | ✅ | `minlength="10"` `maxlength="2000"` |
| 個人情報の取扱いへの同意 | `agree` | `checkbox` | ✅ | `required` |

### バリデーション方針

```html
<label class="c-form__label" for="email">
  メールアドレス <span class="c-form__required">必須</span>
</label>
<input
  class="c-form__input"
  type="email"
  id="email"
  name="email"
  required
  autocomplete="email"
  inputmode="email"
  placeholder="例：info@example.com"
  aria-describedby="email-error"
>
<p class="c-form__error" id="email-error" role="alert" hidden></p>
```

- **HTML標準のバリデーション属性を主とし、JSは「メッセージの日本語化と表示位置の制御」のみ**を担当
- `novalidate` は付けない（JSが失敗してもブラウザが検証する）
- エラーは `aria-invalid="true"` ＋ `aria-describedby` で読み上げに対応
- `placeholder` は**ラベルの代用にしない**（必ず `<label>` を置く）
- **送信先**：静的サイトのためサーバー処理がありません。以下から選択が必要です【ご判断のお願い】
  1. フォーム専用サービス（Formspree / Netlify Forms 等）
  2. 現行サーバーにPHPのメール送信スクリプトを残す
  3. Google フォームへの外部リンクに置き換える
- **スパム対策**：ハニーポット（不可視の入力欄）＋送信までの経過時間チェック。CAPTCHAは最後の手段
